11차시 - Context Window와 Chunking: 문맥 처리 구조



1. Context Window



LLM은 어떻게 문맥을 유지할까?
생성형 AI가 긴 대화를 하거나 긴 문서를 처리할 떄, 문맥을 어떻게 파악하고 유지하는지 이해하는 것이 필요.
-특히, "문맥이 어떤 구조적 조건 아래에서 유지되거나 깨지는지에 초점"
핵심주제: 문맥 유지의 원리와 한계

왜 긴 문서를 넣으면 답변이 흐려질까?
짧은 질문에는 비교적 정확한 답을 하던 모델이, 같은 질문을 긴 문서와 함께 입력하면 갑자기 답변이 모호해지는 경우 발생.
이 현상은 모델의 성능이 갑자기 나빠졌기 때문이 아니라, 입력 길이가 길어졌을 떄 작동하는 구조적 한계와 관련
-요약이 두루뭉술해짐
-중요한 조건을 놓침
-질문과 직접 관련 없는 내용이 섞임

같은 질문, 다른 입력 길이
같은 질문이라도 입력 방식에 따라 결과는 크게 달라짐
짧은 입력 : 핵심을 잘 짚은 답변. 질문 의도와 높은 일치
긴 입력 : 전체를 포괄하려다 논점이 흐려짐. 중요한 정보와 덜 중요한 정보가 섞임.
이 차이는 "모델이 처리해야할 문맥의 양"이 달라졌기 때문.

LLM은 기억하는 모델일까?
많은 사람들이 LLM을 "이전 내용을 기억하는 모델"로 오해함
LLM은 대화를 저장해 두었다가 꺼내 쓰는 방식이 아니라, "현재 입력된 텍스트를 한꺼번에 해석"하는 방식으로 작동
-과거 대화를 기억하는 것이 아님
-다시 입력된 내용만 참고 가능
-기억처럼 보이는 현상은 구조적 착시

모든 입력을 보지만, 무한하지는 않다
LLM은 입력된 텍스트 전체를 보려고 시도하지만 물리적,구조적 한계로 인해, 참고할 수 있는 입력 길이에는 분명한 제한이 존재함
-입력은 모두 텍스트로 들어오지만 내부에서는 일정 길이까지만 유효하게 처리
-이 범위를 넘어가면 일부 정보는 잘리거나 영향력이 급격히 줄어듦

문맥의 한계는 어디서 생기는가?
모델이 기억을 잘하느냐가 아니라, 문맥을 처리할 수 있는 범위와 구조는 어떻게 정해지는가?
1) 왜 일정 길이를 넘으면 성능이 떨어질까
2) 문맥을 유지할 수 있는 범위는 무엇으로 결정될까
3) 이 한계는 실무에서 어떻게 다뤄야 할까

Context Window의 정의
Context Window는 모델이 한 번의 계산에서 Attention할 수 있는 토큰의 최대 범위를 의미함.
이 범위 안에 들어온 입력만이 서로를 참고하며 문맥을 형성함
-한 번에 처리 가능한 입력의 상한선
-이 범위를 벗어나면 문맥 계산에 직접 참여하지 못함 

단어와 토큰은 다르다
모델은 문장을 단어가 아니라 토큰 단위로 처리
토큰은 단어보다 더 잘게 쪼개질 수 있고, 여러 글자가 하나의 토큰이 되기도 함
-단어 =/= 토큰
-같은 문장이라도 언어,표현 방식에 따라 토큰 수가 달라짐
-Context Window는 토큰 개수 기준으로 계산

모델마다 다른 Context Window
모든 LLM이 같은 Context Window를 가지는 것은 아님
모델 설계에 따라 한 번에 처리할 수 있는 토큰 수는 크게 달라짐
-소형 모델 : 비교적 짧은 Context Window
-최신 대형 모델 : 더 긴 문서 처리 가능
하지만 아무리 커져도 "무한하지는 않음"

Attention 범위
Attention은 모든 토큰이 모든 토큰을 참조할 수 있는 구조이지만, 그 '모든 토큰'은 Context Window 안에 있는 토큰으로 제한
-Attention은 무작위가 아님
-범위는 명확히 제한됨
-Context Window 밖 정보는 Attention 대상이 아님



2. 입력길이와 성능



입력이 길어질수록 무엇이 달라질까
입력이 길어진다고 해서 모델의 이해가 자동으로 깊어지지는 않음
오히려 일정 길이를 넘어서면 답변의 정확도와 일관성이 눈에 띄게 떨어짐
-요약이 포괄적으로 변함
-질문의 초점이 흐려짐
-핵심과 주변 정보의 구분 약화

왜 중요한 정보는 희석될까
Context Window 안에 포함된 토큰이 많아질수록, 각 토큰이 차지하는 상대적인 중요도는 낮아짐. 
이로 인해 정말 중요한 정보도 다른 정보들과 섞여 희석
-Attention은 중요도를 나누는 구조
-토큰 수 증가 -> 집중도 분산
-핵심 정보가 "눈에 띄지 않게" 됨

문맥 유지 실패는 어떻게 나타날까
문맥이 붕괴되면 모델은 겉보기에 그럴듯한 답변을 하지만. 앞에서 설정한 조건이나 전제를 어기는 답변을 생성
-초반 조건과 모순되는 결론
-인물,대상 혼동
-요약 대상이 중간에 바뀜

긴 입력 =/= 더 좋은 이해
입력이 길어질수록 모델은 더 많은 정보를 받지만, 그 정보를 더 잘 이해하지 않음
-길이는 도움이 되기도, 방해가 되기도 함
-구조를 고려하지 않은 긴 입력은 오히려 독이 됨
정보량 증가 =/= 이해도 증가

길이 문제는 구조 문제
입력 길이에 따른 성능 저하는 모델의 능력 부족 문제가 아님
이는 Context Window와 Attention 구조에서 자연스럽게 발생하는 구조적 한계

문제의 원인: 입력 길이 자체가 아님
진짜 원인: 문맥을 처리하는 구조			-> 	Chunking
해결방향: 길이를 줄이거나, 구조를 나누는 방법 



3. Chunking의 필요성



긴 문서를 그대로 넣는 방식의 한계
긴 문서를 한번에 입력하면 모델은 더 많은 정보를 받지만, 그 정보를 같은 수준으로 이해하지는 못하며 문맥 붕괴와 정보 희석은 입력 방식에서 이미 시작됨
-한 번에 너무 많은 토큰이 들어옴
-핵심과 부수 정보가 섞임
-Attention이 분산되어 초점 상실

Chunking 개념
Chunking = 의미 단위 분할
긴 문서를 의미가 완결되는 단위로 나누는 전처리 전략
문단, 주제, 섹션처럼 자연스러운 경계를 기준으로 분할
-길이 기준이 아니라 의미 기준
-각 Chunk는 독립적으로 이해 가능
-이후 단계에서 결과를 결합

문맥 유지를 위한 구조적 전처리
Chunking은 모델의 성능을 높이는 기법이라기보다, 모델이 가진 구조적 한계를 피해서 입력을 설계하는 방법임
-Context Window 초과 방지
-Attention 분산 최소화
-각 Chunk 안에서 문맥 밀도 유지
모델이 "집중할 수 있는 환경"을 만들어줌

전체 입력 vs Chunk 입력
같은 문서라도 입력 구조에 따라 결과는 다르게 나옴
전체 입력 : Attention 분산, 핵심 정보 약화
Chunk 입력 : 집중된 처리, 핵심 유지

Chunking은 기억을 돕는 전략
Chunking은 모델에게 기억을 추가해 주는 방법이 아님. 대신, 모델이 가진 제한된 문맥 처리 능력을 효율적으로 쓰게 만드는 전략.
기억을 늘리는 방식 (X), 집중을 설계하는 방식 (O)



4. Chunking 방식 이해



Chunking에는 대표적으로 두 가지 방식이 있음
1) 길이 기준으로 기계적으로 다루는 방식
2) 의미가 끝나는 지점 기준으로 나누는 방식
고정 길이 Chunk : 일정 토큰 수마다 분할. 구현이 간단, 문맥이 중간에서 끊길 위험. ex) 1000 토큰마다 자르기
의미 기반 Chunk : 문단, 주제 단위로 분할. 문맥 보존에 유리, 사전 판단이 필요. ex) 소제목 1개 = 1 Chunk

Chunking 크기
Chunk는 작을수록 안전하지만, 너무 작으면 정보가 흩어짐. 반대로 크면 정보는 풍부하지만 문맥 붕괴 위험이 커짐
작은 Chunk : 문맥 안전성 높음, 전체 맥락 파악 어려움 -> 검색, 질의 응답
큰 Chunk : 정보량 많음, Context Window 초과 위험 -> 요약 목적

Overlap 개념
Chunk를 나누면 자연스럽게 경계 문제가 발생
앞 Chunk의 마지막 정보와 뒤 Chunk의 첫 정보가 단절될 수 있음
이를 보완하기 위해 일부 구간을 겹쳐서(overlap) 포함시키는 방식을 사용
-Chunk 간 연결 보완
-문맥 흐름 유지 목적

Overlap 효과
Overlap은 중복이 아니라 연결 장치 역할
모델을 겹치는 부분을 기준으로 앞뒤 Chunk의 맥락을 자연스럽게 이어서 이해
ex) 회의록 요약에서 이전 결졍 사항이 다음 논의에 반영됨

Chunking 설정이 결과에 미치는 영향
같은 문서라도 Chunk 설정에 따라 결과 품질은 크게 달라짐
Chunk가 너무 큰 경우 : 요약 누락, 문맥 붕괴 발생
Chunk가 너무 작은 경우 : 파편화된 요약, 전체 흐름 약화
적절한 크기 + overlap -> 안정적인 문맥 유지

좋은 Chunking의 기준
좋은 Chunking에는 정답이 없으나, 지켜야 할 기준은 존재함
-Context Window를 넘지 않을 것
-의미 단위가 깨지지 않을 것
-필요한 경우 overlap을 사용할 것
-목적(요약,검색,QA)에 맞게 설계할 것
Chunking은 단순한 전처리가 아니라 "LLM과 소통하는 방식 자체를 설계하는 작업"



5. 긴 문서 처리 실습



동일한 긴 문서를 사용해, 입력 방식을 달리했을 때 요약 결과와 문맥 유지가 어떻게 달라지는지를 비교하기
-긴 문서를 한 번에 입력했을 떄의 한계 관찰
-Chunk 단위로 나누었을 때의 변화 확인
-실무에서 활용 가능한 입력 전략 도출

전체 입력
먼저 긴 문서를 나누지 않고 한번에 입력해 요약을 요청. 긴 입력에서 발생하는 전형적인 문제를 직접 관찰

|| 다음 문서를 읽고 핵심 내용을 요약해주세요 ||
요약 형식:
1. 문서의 주제와 목적
2. 핵심 논점 (3~5개)
3. 결론 또는 제안사항
4. 중요한 데이터나 통계 (있는 경우)

평가
1) 핵심 논점이 모두 반영되는가
2) 결론이 명확한가
3) 요약이 지나치게 추상적인가

Chunk 입력
같은 문서를 의미 단위로 나누어 처리
1단계 : 문서를 2~3개의 의미 덩어리로 분리해서 각 Chunk를 독립적으로 요약
2단계 : 요약 결과만을 사용해 전체 요약 생성

|| 다음은 긴 문서의 일부입니다. 이 부분의 핵심 내용을 요약해주세요. ||
1. 주요 내용과 논점
2. 중요한 데이터나 사실
3. 이 섹션의 결론
|| 아래는 문서 각 부분의 요약입니다. 이를 바탕으로 전체 문서를 종합적으로 요약해주세요. ||

전체 입력 vs Chunk 입력 결과 비교
전체 입력 요약 : 구조는 유지되지만 세부 누락 가능. 결론이 흐려질 수 있음
Chunk 기반 요약 : 논점이 분리되어 명확. 종합 단계의 중요성 증가
|| 비교 기준 ||
1) 핵심 내용 포함 여부
2) 결론이 명확한가
3) 요약이 지나치게 추상적인가

문맥 유지 실패 사례
다음과 같은 실패가 반복적으로 관찰되면 문맥 유지 실패
-앞부분에서 제시한 조건이 결론에서 사라짐
-사례와 주장, 결론이 뒤섞임
-"논의되었다" 수준의 추상적인 요약
-실행 계획 또는 핵심 메시지 누락
모델의 성능이나 프롬프트가 아닌, 입력 구조가 문맥을 결정함
