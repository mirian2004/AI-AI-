13차시 - 검색과 생성을 연결하는 구조 : RAG 이해



1. RAG 구조 다이어그램



생성형 모델 단독 사용
생성형 AI는 질문을 입력 받아 내부에 학습된 지식을 기반으로 바로 문장을 생성함. 외부 자료를 실제로 확인하지 않음

생성형 AI의 문제점 : 환각(Hallucination)
생성형 AI는 모르면 모른다고 말하지 않고 그럴듯한 답을 만들어냄. 틀린 정보라도 확신에 찬 답변 발생.

임베딩 검색의 한계 : 사용자의 추가 해석 필요
임베딩 검색은 질문과 가장 가까운 문서 조각을 찾는 기술. 
하지만 검색 결과 자체는 답변이 아님. 문서를 읽고 말해주는 단계가 없음.

해결방법
"생성 모델과 검색 시스템, 이 둘을 같이 쓴다면?"
생성 모델 : 근거 없는 답 도출 위험
검색 시스템 : 단순 문서만 나열

RAG의 정의
RAG = Retrieval + Generation
Retrieval : 질문과 관련된 정보를 찾음
Generation : 찾은 정보를 바탕으로 답변을 생성
Query -> Retrieval -> Documents -> Generation -> Answer

RAG의 핵심 아이디어
"기억하지 않고, 찾아서 말한다."
-모든 내용을 생성형 AI에게 미리 학습시키지 않음
-필요할 떄 질문과 관련된 정보를 찾아서, 찾은 정보를 바탕으로 답변

RAG의 필요성
최신성 : 학습 이후 정보도 활용 가능
정확성 : 실제 문서를 근거로 답변
근거 제시 : "왜 이런 답이 나왔는지" 설명 가능
 


2. 임베딩 DB 구축



RAG 파이프라인
RAG는 크게 두 구간으로 나뉨
-데이터 준비 : 문서를 검색 가능한 형태로 준비
-검색 및 생성 : 질문이 들어왔을 떄 답변 생성

임베딩
임베딩은 텍스트를 숫자 벡터로 변환
-컴퓨터는 문장의 의미를 직접 비교할 수 없음.
-숫자 벡터 간의 거리는 비교 가능.
의미가 비슷할수록 벡터 간 거리가 가까움

벡터 DB
임베딩된 문서들을 저장하는 공간
-기존 DB와의 차이는 키워드 일치가 아닌 의미 기반 거리 검색
-FAISS를 사용해 벡터 검색 수행 -> FAISS는 Facebook에서 개발한 벡터 유사도 검색을 위한 라이브러리

질문 처리 흐름
사용자의 질문(User Query)도 문서와 동일한 처리 과정을 거침 -> 질문과 문서는 같은 벡터 공간에서 질문 벡터와 문서 벡터 간의 거리를 계산함
1) 질문 입력
2) 임베딩 모델로 변환
3) 벡터 DB에서 검색

Retrieval(검색)의 역할
Retrieval : 관련 있는 정보를 고르는 것
-Retrieval은 문장을 만들거나 답변을 요약하지 않음
-Retrieval은 질문과 가장 가까운 문서를 찾는 과정

검색 품질이 중요한 이유
RAG에서 자주 발생하는 문제: 검색 실패 -> 답변 실패
-LLM은 주어진 정보 안에서만 답변 생성
-RAG 성능의 절반은 Retrieval 품질

Generation 역할
Generation은 외부에서 새 정보를 가져오지 않음
입력으로 들어온 것만 사용: 질문(Query), 검색 결과(Context)
정확도를 높이려면 Prompt에 규칙을 넣기. ex) 정보에 없는 내용은 모른다고 답하라.

Context
Generation 단계에서는 Retrieval 과정으로 얻어낸 참고 정보(Context)를 프롬프트(Prompt)에 넣어서 답변을 생성함
기본 구성 : 규칙(Guardrail), 참고정보(Context), 질문(Query)
프롬프트가 깔끔할수록 답변이 근거 중심으로 정리됨

Retrieval vs Generation
Retrieval : 질문과 관련 있는 문서 조각을 찾아오는 단계
-출력 : Context(참고 정보)
Generation : Context를 근거로 답변을 문장으로 쓰는 단계
-출력 : Answer(최종 답변)



3. Q&A 파이프라인 실습



[실습] 전체 Q&A 파이프라인
1) 벡터 DB에 문서(지식) 저장
2) 질문 임베딩 생성
3) 벡터 DB 검색을 통한 관련 문서 조각(Context) 획득
4) Context 와 질문을 결합한 프롬프트 입력
5) LLM을 통한 최종 Response 출력

목표 : RAG 시스템의 작동 여부 검증
실습을 통한 결과 지표 : 검색된 문서 조각 (Context), 최종 답변 (Answer)
-> 질문에 대한 문서 조각을 잘 찾았는지 확인 



4. 검색 정확도 및 응답 품질 비교



생성 단독 vs RAG
같은 질문을 두 방식으로 비교
생성 단독 - 질문만 LLM에 입력 vs RAG - [검색 결과 + 질문] 입력
비교 기준
-정답 여부
-근거 제시 여부
-답변의 안정성(일관성)

결과 비교: 정확도 차이
문서 내용을 질문하는 경우, 생성 결과의 정답 여부 확인
생성 단독 : 문서 내용과 달라 답변 정답률이 낮음
RAG : 검색된 문서 범위 안의 답변 정답률이 높음
"정보가 문서에 있을수록 RAG가 유리"

결과 비교 : 환각 여부
문서에 없는 질문의 경우, 두 방식에서의 답변 차이 확인
생성 단독 : 실재하지 않은 내용도 추측하여 답변
RAG : 프롬프트 규칙에 따라 정보에 없으면 답변 X
"환각은 검색 부재와 생성 단독에서 발생"

결과 비교 : 재현성 비교
동일 질문을 3회 이상 반복 실행 시, 답변 내용의 일관성 비교
생성 단독 : 매 실행 시마다 표현과 내용이 변화
RAG : 동일한 Context에서 일정한 답변 제공
"답변의 논리적 근거가 고정된 RAG"

RAG의 장단점
정확성을 얻는 대신, 복잡한 구조의 파이프라인 설계가 필요
장점 : 근거 기반 답변, 최신 정보 활용 가능, 환각 감소
단점 : 복잡한 구조, 검색 품질 관리 필요
